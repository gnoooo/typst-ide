# crates/app (Tauri application shell)

This crate is the desktop application entry point. It bridges the web frontend (Monaco + JS) with the business logic exposed by [`crates/core`](../core).

## Role

- Initializes the Tauri window and serves `frontend/dist` as the UI
- Exposes **Tauri commands** callable from JS via `invoke()`
- Manages shared application state (SQLite connection, etc.)
- Contains **no compilation logic** everything goes through `typst-ide-core` (which is [`crates/core/src/compiler`](../core/src/compiler/))

## Exposed Commands

### Compilation / Preview

| Command | Return | Description |
|---|---|---|
| `render_preview(source)` | `Result<String, Vec<DiagnosticInfo>>` | Compiles Typst source to HTML (inline SVGs per page). Runs on a blocking thread pool to avoid freezing the UI. |
| `export_pdf(source, path)` | `Result<(), String>` | Compiles to PDF and writes the file to the given path. |
| `pick_pdf_path()` | `Option<String>` | Opens a native "Save As" dialog filtered to `.pdf`. |

### Project Management

| Command | Return | Description |
|---|---|---|
| `open_folder_dialog()` | `Option<String>` | Native folder picker dialog. |
| `create_project(name, base_path, content?)` | `Result<String, String>` | Creates a project directory with a `main.typ` file. |
| `open_project(dir_path)` | `Result<ProjectInfo, String>` | Reads the first `.typ` file found in the directory. |
| `save_file(path, content)` | `Result<(), String>` | Writes a file, creating missing parent directories. |

### Notes (SQLite)

| Command | Description |
|---|---|
| `add_note(title, content, scope, project_id?)` | Adds a note |
| `get_all_notes()` | Returns all notes |
| `get_global_notes()` | Returns notes not linked to any project |
| `get_project_notes(project_path)` | Returns notes linked to a project |
| `get_current_project_id(project_path)` | Hashes the project path into a stable ID |
| `delete_note(note_id)` | Deletes a note |
| `update_note(note_id, title, content, scope, project_id?)` | Updates a note |

### Utilities

| Command | Return | Description |
|---|---|---|
| `font_exists(name)` | `bool` | Checks whether a font family is available on the system. |

## Managed State (`tauri::State`)

| Struct | Inner type | Role |
|---|---|---|
| `NotesDbState` | `Mutex<rusqlite::Connection>` | SQLite connection shared across note commands |

The database is initialized on startup inside `app_data_dir()` (e.g. `~/.local/share/typst-ide/notes.db` on Linux).

## Configuration (`tauri.conf.json`)

- **Frontend dist** : `../../frontend/dist`
- **Dev URL** : `http://localhost:1420`
- **Bundle targets** : `appimage` (Linux), `deb` (Linux), `rpm` (Linux), `nsis` (Windows, via cross-build `--target x86_64-pc-windows-gnu`)
- **Desktop file** : `deb` and `rpm` (and therefore the AppImage) use the repository's `typst-ide.desktop` as a Handlebars template
- **Identifier** : `com.typst.ide`

## Build Commands

Prefer the project wrapper, which handles the frontend build, the AppImage post-processing (`scripts/fix-appimage.sh`), the Windows cross-build and the containerized release environment:
```bash
# From the repository root
./manage.sh build                                  # native bundles; + Windows if the cross toolchain is present
./manage.sh build appimage                         # single bundle (AppImage post-processed)
./manage.sh build windows                          # NSIS installer + portable .exe (MinGW, cross-compiled from Linux)
./manage.sh build windows --container              # same but MSVC via cargo-xwin (CI-like, self-contained)
./manage.sh build appimage,deb,rpm,windows --container   # everything in the release container
./manage.sh build rust                             # frontend + cargo release only
```

Under the hood (from `crates/app/`):
```bash
# Development (with frontend hot-reload)
cargo tauri dev

# Release bundles (default: all targets from bundle.targets)
cargo tauri build       # Linux -> .AppImage + .deb + .rpm (nsis skipped: it needs the Windows target)

# Select a specific bundle (or several, comma-separated)
cargo tauri build --bundles appimage
cargo tauri build --bundles deb,rpm

# Windows .exe (NSIS installer, cross-compiled from Linux)
cargo tauri build --bundles nsis --target x86_64-pc-windows-gnu
```

> The Windows cross-build needs the cross toolchain and the Rust standard
> library for the target:
>
> ```bash
> # Fedora
> sudo dnf install mingw64-gcc mingw64-gcc-c++ mingw64-binutils mingw64-winpthreads rust-std-static-x86_64-pc-windows-gnu mingw32-nsis
> # Arch
> sudo pacman -S mingw-w64-gcc nsis  &&  rustup target add x86_64-pc-windows-gnu
> ```
>
> On Linux Tauri calls the system `makensis`, which must ship the NSIS stubs
> (on Fedora `makensis` comes from `mingw-nsis-base`, the stubs from `mingw32-nsis`). No host dependency at all with `./manage.sh build windows --container`: the release container cross-compiles to the MSVC target with `cargo-xwin` (Tauri's documented method) and produces the same kind of self-contained portable as the CI. 
> With the MinGW host build, the portable `Typst IDE_<version>_x64-portable.exe` needs the `WebView2Loader.dll` sitting next to it in `release/`.
> See `docs/windows-build.md`.
>
> `frontend/dist` must be built beforehand (`npm run build` in `frontend/`), otherwise the bundle step fails. Like CI, use `NO_STRIP=1 cargo tauri build` when the release profile sets `strip = true`.
>
> A bare `cargo tauri build` leaves the AppImage in its stock form (WebKitGTK bundled, Wayland libraries included). 
> Run `./manage.sh fix-appimage` (or the `./manage.sh build appimage` command above) to apply the AppImage conventions before distributing it, see `docs/appimage.md`.
